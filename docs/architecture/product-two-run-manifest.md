# Product 2 status and run-manifest contract

This document freezes the top-level vocabulary and minimum identity needed to
interpret a Product 2 result. It does not replace lower-level parser,
preflight, lowering, objective, or qualification reports; those reports retain
their native status fields and evidence detail.

## Top-level status vocabulary

| Status | Meaning | Runtime started? | Consumer action |
| --- | --- | ---: | --- |
| `passed` | The requested execution completed without a runtime error. | Yes | Inspect the artifact and declared evidence boundary. |
| `development` | Evidence exists, but the scenario or fidelity remains a development-level result. | Usually | Do not promote it to qualification. |
| `blocked` | A required input, binding, or precondition prevented execution from starting. | No | Follow the diagnostic remediation. |
| `incomplete` | Execution started but stopped before its requested completion without an explicit envelope disposition. | Yes | Inspect termination and step-limit diagnostics. |
| `out_of_envelope` | Execution stopped because a declared model, source, or terminal envelope was reached. | Yes | Treat the bounded outcome as evidence, not as an unexpected crash. |
| `failed` | Execution started and encountered an error or invalid runtime result. | Yes | Inspect the failure diagnostics and reproduce with the same manifest. |

`development` is an evidence-maturity status, not a synonym for a successful
runtime. A completed pseudo-6DOF run may therefore have a runtime outcome of
`passed` while its scenario/evidence status remains `development`.

The implementation is `taoryx.product_two_contracts.ProductTwoStatus`. The
source-file runner emits its runtime outcome in `RunReport.status` and the
serialized report under `status`.

## Minimum run manifest

The reserved manifest identifier is
`taoryx.product-two-run-manifest/v1alpha1`, with integer
`schema_version: 1`. A conforming manifest must contain these top-level fields:

| Field | Required content |
| --- | --- |
| `schema` / `schema_version` | Manifest identifier and compatibility version. |
| `scenario_id` | Stable catalog or caller-owned scenario identity. |
| `status` | One of the six Product 2 statuses above. |
| `expected_disposition` | Expected result for the scenario, using the same vocabulary. |
| `operation` | `batch`, `interactive`, `composition_batch`, or `composition_episode`. |
| `fidelity` / `realization` | Explicit fidelity tier and realization type; never inferred from plots. |
| `source_inputs` | Every problem, table, sidecar, composition, or model input with path/URI and SHA-256. |
| `run_identity` | Stable identity for this exact input/configuration/action stream. |
| `runtime` | Runtime version, git revision, Python/platform identity, and host-independent execution metadata. |
| `integration` | Integrator, `dt`, `dtprnt`/output cadence, maximum steps, and seed where applicable. |
| `time` | Requested duration plus accepted start/end truth time. |
| `termination` | Completion flag, reason, event/envelope code, and diagnostic references. |
| `artifacts` | Named output paths, artifact kind, byte size, and SHA-256. |
| `claim_boundary` | Explicit positive result and nonclaim text. |

### Compatibility policy

- Readers must reject an unknown `schema` or unsupported major version with a
  diagnostic that names the received and supported identifiers.
- Additive fields are allowed within the same major schema version; readers
  must preserve unknown fields when forwarding a manifest.
- Removing or changing the meaning of a required field requires a new schema
  identifier or major version.
- The top-level `status` is closed and case-sensitive. Lower-level native
  statuses may appear under diagnostic or evidence sections but must not replace
  the top-level Product 2 status.
- Paths are provenance references, not portable identities. The SHA-256 and
  stable `run_identity` are the reproducibility anchors.
- A valid manifest proves identity and disposition metadata. It does not prove
  numerical accuracy, physical-effector behavior, vehicle qualification, or
  historical fidelity.

Numerical evidence is carried separately by the M4
`taoryx.product-two-numerical-quality/v1alpha1` report described in
[Product 2 numerical quality and fidelity gates](product-two-quality-gates.md).
That report may classify a manifest-backed run as `development`, `blocked`, or
`bounded-failure`; a completed manifest status never promotes the result by
itself.

## M0 baseline evidence

The canonical baseline report is
`verification/product_two_baseline.json`. It is generated by
`tools/build_product_two_baseline.py` and records, for each canonical scenario:

- command identity and expected disposition;
- observed Product 2 status and process exit code;
- wall-clock duration;
- output/artifact file count and byte size;
- SHA-256 for the normalized artifact where one exists; and
- a repeatability comparison for the same inputs and configuration.

The report is a release baseline, not a qualification packet. Timing values are
diagnostic and should be compared on the same host class; identity, status,
artifact shape, and repeatability are the stronger M0 gates.
