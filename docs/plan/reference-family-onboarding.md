# Source-grounded reference-family onboarding

Status: Alpha 3 onboarding slice

This plan folds the F-16 S-119 and HL-20 Mod K packages into Taoryx without
silently promoting them to the maturity of the four established showcase
vehicles.

The reusable composition procedure is documented in the
[generic family-integration playbook](generic-family-integration-playbook.md).
That playbook defines the data contract, explicit fidelity lowering policy,
trim and diagnostic ladder, controller binding, and showcase promotion path.

## Two catalog boundaries

The executable vehicle registry in `verification/vehicle_models.yaml` remains
the catalog for the standard local runtime vehicles: X8, B747, Hummingbird,
and X-15. Those entries carry the native geometry, table, controller-profile,
and scenario contracts used by the existing vehicle checks.

The source-grounded reference catalog in
`verification/reference_family_catalog.yaml` contains pinned DAVE-ML family
packages. F-16 S-119 and HL-20 Mod K are already selectable through this
provider-neutral family interface and have source-package replay evidence.

`verification/supported_reference_families.yaml` is the explicit bridge between
those catalogs. It records the physical family, evidence strength, maturity,
supported fidelity profiles, nonclaims, and next gate. A reference family is
therefore *supported* without being represented as a fully qualified local
vehicle.

## Current support boundary

| Family | Physical family | Supported now | Still pending |
|---|---|---|---|
| F-16 S-119 | powered fixed-wing | source-grounded replay; 3DOF and pseudo-6DOF nominal racetrack; local physical-surface T5 development pass | multi-point scheduled nonlinear control, source-backed actuator data, R1/release robustness, batch/step parity, family promotion |
| HL-20 Mod K | unpowered lifting body | source-grounded rigid-body 6DOF replay; logical surface-allocation contract | validated allocator/controller, glide guidance and arrival showcase, 3DOF/pseudo-6DOF reductions, landing/contact |

The replay claim is deliberately narrower than a vehicle qualification claim.
The DAVE-ML source force/moment graph and fixed mass-property binding are
verified within each manifest's declared envelope. Source actuator dynamics,
production controls, operational performance, and unsupported terminal behavior
remain nonclaims.

## Promotion path

1. Keep the source package and family manifest byte-pinned.
2. Build the family-specific trim and operating-point evidence.
3. Derive and validate the declared reduced-fidelity profiles.
4. Replace direct source-control inputs with bounded physical effector models
   where the source data support them.
5. Run the common mission/objective evaluator and evidence-board renderer.
6. Promote maturity only after the corresponding evidence tier passes; a
   selectable manifest or a stable matrix shape is not sufficient.

## F-16 integration work log

The first operating point is now explicit at
`families/reference_f16_s119/qualification/operating-points.yaml`.

Completed evidence:

- source package and DAVE-ML force/propulsion/mass bindings are pinned;
- source runtime replay is verified;
- sea-level, 152.4 m/s force/moment equilibrium trims with alpha,
  elevator, and source power;
- the trim state is resolved into body velocity, attitude, and zero body rates;
- the source throttle convention is recorded as percent, with the canonical
  Taoryx throttle remaining a normalized fraction.
- body gravity is resolved in FRD at the trimmed pitch angle; the old
  `force_z + mg`-only screen has been replaced for this operating point.
- propulsion is evaluated at the operating-point Mach (`0.44787`), rather
  than the former Mach-zero placeholder; the resulting source throttle is
  `8.9323%`.
- a source-backed runtime load/derivative adapter now computes dynamic
  pressure, alpha/beta, Mach, source controls, FRD gravity, and Newton-Euler
  body derivatives from canonical SI state/control names.
- the adapter is now bound to the shared rigid-body state: ECIC velocity is
  resolved into source body axes, source loads are reported as decomposed
  body force/moment components, quaternion and body-rate propagation uses the
  common runtime model, and the source full symmetric inertia matrix (including
  the nonzero `I_xz` product) is retained.
- `verification/f16_runtime_linearization_evidence.json` is now generated by
  `taoryx daveml-f16-runtime-linearization`; its two-step derivative check
  records the runtime plant ID, state/control ordering, units, matrices, and
  the explicit non-qualification boundary.
- `families/reference_f16_s119/controllers/local-lqr-trim-hold-v1.yaml` and
  `families/reference_f16_s119/actuators/reference-first-order-v1.yaml` now
  define the first bounded closed-loop development screen. The generated
  `verification/f16_lqr_trim_hold_evidence.json` demonstrates a Hurwitz,
  plant-derived LQR driving explicit elevator, aileron, rudder, and throttle
  commands through position/rate/lag overlays into the nonlinear source plant.
  This is deliberately `development_screen` evidence: the actuator values are
  engineering assumptions, this particular screen bypasses the desired-wrench
  allocator, and it is not a scheduled or flight-qualification result.
- `taoryx daveml-f16-physical-allocation` now generates
  `verification/f16_physical_allocation_evidence.json`. The F-16 adapter
  derives a four-axis local effectiveness matrix directly from centered
  source-load perturbations for body-axis force plus roll, pitch, and yaw
  moments. The packet includes a feasible trim witness and a deliberately
  infeasible demand that is reported as partially achievable with residuals
  and saturated channels. This proves the allocation seam, not closed-loop
  maneuver performance.
- `taoryx daveml-f16-physical-wrench-lqr` now generates
  `verification/f16_physical_wrench_lqr_evidence.json`. A small declared
  perturbation is converted by plant-derived LQR into a desired body-force /
  moment demand, solved through the bounded effector allocator, advanced
  through actuator lag/rate models, and integrated through the source
  nonlinear derivative. The witness closes with all samples feasible and no
  saturation, but remains a single local development screen.
- `taoryx daveml-f16-physical-wrench-perturbations` now generates
  `verification/f16_physical_wrench_perturbation_evidence.json`. The fixed
  matrix covers isolated longitudinal, normal, and pitch-rate perturbations,
  a coupled reversal, and a lateral coupled case. All five witnesses reduce
  their normalized feedback error by the declared factor without allocation
  infeasibility or actuator saturation. This is still a local operating-point
  result, not an envelope or maneuver qualification.
- `taoryx daveml-f16-local-maneuvers` now generates
  `verification/f16_local_maneuver_evidence.json`. The sequence exercises
  trim hold, both signs of local roll-rate response, both signs of pitch-rate
  response, and recovery through the same allocator and actuator overlay.
  These are transient body-rate witnesses; they intentionally do not claim
  route translation, attitude-angle closure, scheduled guidance, or flight
  qualification.
- `taoryx daveml-f16-reductions` now generates
  `verification/f16_reduction_evidence.json`. The point-mass reduction
  preserves the source translational force channels at the matched operating
  point, while the named pseudo-6DOF reduction uses a source-derived local
  linear rate-response bridge plus kinematic attitude propagation. The local
  elevator, aileron, rudder, and throttle pulse witnesses pass with a maximum
  relative rate error below 0.06%, but both reduction contracts remain
  `equivalence_pending` until a mission-window comparison is available.

Remaining to behave like the B747/X8 integration path:

1. Compare the allocator-backed recovery against the direct-effector screen
   over isolated and coupled perturbations, including deliberately
   infeasible demands.
2. Replace the development actuator bounds and lag with source-backed data
   where available, retaining provenance for any engineering assumptions.
3. Bind the fixed-wing guidance/controller stack and prove trim-hold,
   reversal, and authority tests before adding the racetrack segments.
4. Extend the local reduction screen into matched parent/reduction mission
   windows, then promote the 3DOF and pseudo-6DOF profiles only if their
   declared comparison gates pass.
5. The subsonic F-16 racetrack packet now exists at all four declared
   comparison tiers. Promote it only after the remaining schedule, robustness,
   replay, and claim-review gates pass.

The F-16 now has four explicit, preflightable bindings in the shared
`powered_fixed_wing_racetrack_v1` catalog. They use a long, high-speed course
with a 12 km straight, 3.5 km semicircle turns, a 300 m altitude step, and
20-degree signed turn-bank targets. The route adapter, truth evaluator, and
four-tier packet are now present. The source runtime remains a fixed-altitude
local fixture, so the route result is a local development witness rather than
an all-envelope mission qualification.

The next route slice is:

1. add a source-aware F-16 mission adapter that consumes the resolved shared
   racetrack rather than copying X8/B747 route constants;
2. expose local north/east/altitude and phase channels from the same truth
   state used by the source plant;
3. run the point-mass and pseudo-6DOF reductions against the parent for a
   matched short mission window;
4. add direct-wrench and surface-allocation route witnesses only after the
   local guidance references remain inside the operating-point envelope; and
5. pass the resulting telemetry through the existing independent objective
   evaluator and evidence-board renderer.

The exact missing work is therefore not another trim solve. It is the bridge
from one fixed operating point to a scheduled powered-fixed-wing controller:
an operating-point catalog, a guidance reference that produces bounded bank,
flight-path, and speed demands, physical surface allocation at each point, and
an independent racetrack evaluator. Until that bridge exists, the F-16 should
remain selectable as a source-grounded rigid-body reference and as a local
development reduction, but not as a qualified powered-fixed-wing route model.

The full-state wrapper is still a local fixed-altitude fixture. It does not
claim geocentric position/gravity coupling, fuel burn, engine transients, or
physical actuator motion until those source-backed contracts are added.

Important diagnostic: the current equilibrium trim's `power_pct` value is a
source percent value. It must not be passed as a normalized throttle fraction
without the explicit 100x binding conversion.
